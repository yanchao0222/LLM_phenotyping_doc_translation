# Prompt 1 — Extract the Source-Grounded Phenotype Specification






You are an expert in clinical phenotyping, epidemiology, and the OMOP Common Data Model.

Your task is to extract the complete phenotyping algorithm for identifying **cases and controls for Type 2 Diabetes Mellitus** from the attached PDF file or files.

The PDF is the sole source of truth. Do not use outside clinical knowledge to add, modify, or complete the phenotype definition.

## Objectives

1. Identify every criterion that is part of the case or control definition.
2. Determine exactly how the criteria are logically and temporally combined.
3. Distinguish the final phenotype algorithm from background information, exploratory analyses, validation methods, and descriptive statistics.
4. Produce a source-grounded, implementation-ready phenotype specification.
5. Preserve all code lists, thresholds, counts, exclusions, and time windows without abbreviation or truncation.

## Extraction Requirements

Review all relevant content, including:

* Main text
* Methods
* Tables
* Figures
* Flow diagrams
* Footnotes
* Appendices
* Supplementary definitions contained in the provided files

Extract, when present:

* Inclusion criteria
* Exclusion criteria
* Case criteria
* Control criteria
* Index-date definition
* Required event counts
* Whether qualifying events must occur on distinct dates
* Minimum or maximum time between events
* Lookback and follow-up periods
* Age, sex, race, or other demographic restrictions
* Observation or enrollment requirements
* Diagnosis codes
* Procedure codes
* Drug or ingredient codes
* Laboratory-test codes and value thresholds
* Symptom or clinical finding codes
* Encounter or care-setting restrictions
* Provider-specialty restrictions
* Disease-free or washout periods
* Rules for resolving multiple possible index dates
* Any hierarchy, descendant, or code-range logic
* Any criteria applied only to cases or only to controls
* Any rule preventing a person from qualifying as both a case and a control

Do not infer a criterion merely because it is clinically reasonable.

## Concept and Code Rules

1. Use OMOP domains and concepts to categorize diagnoses, procedures, measurements, observations, medications, visits, devices, and other clinical events.
2. Do not invent OMOP `concept_id` values.
3. Preserve every code exactly as written in the PDF.
4. Record the source vocabulary when it is explicitly provided, such as ICD-9-CM, ICD-10-CM, CPT, HCPCS, LOINC, RxNorm, or NDC.
5. Do not guess the vocabulary when it is not stated or cannot be determined from the PDF.
6. When both a concept name and a code are provided, use the code in machine-readable logic. The name may appear only in explanatory comments or the evidence table.
7. Do not replace explicit code lists with concept names.
8. Do not abbreviate code lists with phrases such as “and others,” “etc.,” or ellipses.
9. Do not expand code ranges, include descendants, or add related concepts unless the source explicitly requires that behavior.
10. Clearly distinguish literal source codes from any later OMOP standard-concept mapping.

## Required Output

### A. Phenotype Overview

Provide:

* Phenotype name
* Study population, when defined
* Unit of classification, such as person, encounter, or episode
* Case definition summary
* Control definition summary
* Index-date summary
* Relevant source sections, tables, figures, and pages

### B. Source Evidence Matrix

Create one row for each atomic criterion with these fields:

* Criterion ID
* Case, control, or shared criterion
* Criterion type
* OMOP domain
* Source vocabulary
* Exact code or complete code list
* Required count
* Distinct-date requirement
* Value or threshold
* Temporal relationship
* Inclusion or exclusion
* Source page
* Source section, table, figure, or appendix
* Grounding notes

Use concise paraphrases rather than unsupported interpretation.

### C. Logical Phenotype Specification

Express the algorithm in SQL-style Boolean logic, but do not yet produce the final executable database query.

Use explicit structures such as:

```sql
CASE_DEFINITION :=
    POPULATION_REQUIREMENTS
    AND CASE_INCLUSION_CRITERIA
    AND NOT CASE_EXCLUSION_CRITERIA;

CONTROL_DEFINITION :=
    POPULATION_REQUIREMENTS
    AND CONTROL_INCLUSION_CRITERIA
    AND NOT CONTROL_EXCLUSION_CRITERIA
    AND NOT CASE_DEFINITION;
```

Replace the example structure with the actual source-grounded logic.

Explicitly represent:

* `AND`
* `OR`
* `NOT`
* Counts
* Distinct dates
* Date windows
* Before-or-after relationships
* Index-date selection
* Exclusions
* Case-control precedence

Do not simplify logic when doing so could change the phenotype.

### D. Ambiguities and Missing Information

List every implementation-relevant detail that the PDF does not define clearly.

For each ambiguity, state:

* What is unclear
* Where the ambiguity appears
* Why it matters for implementation
* Whether an executable implementation can proceed without inventing information

Do not resolve ambiguities using outside knowledge.

## Quality-Control Checklist

Before responding, verify that:

* Every criterion is supported by the PDF.
* Every code is copied accurately.
* No code has been omitted.
* No external clinical criterion has been added.
* Case and control logic are separated clearly.
* All counts and time windows are explicit.

# Prompt 3 — Generate Read-Only Executable OMOP SQL





Using only the **Verified Phenotype Specification** produced in the preceding step, generate executable SQL that identifies cases and controls in an EHR database conforming to the OMOP Common Data Model.

Do not reinterpret the original PDF at this stage unless needed to resolve a direct transcription inconsistency. Do not add clinical criteria that are absent from the verified specification.

## SQL Environment

Use the following settings when provided:

* Target SQL dialect: `[SQL_DIALECT]`
* OMOP CDM version: `[OMOP_CDM_VERSION]`
* OMOP CDM schema: `[CDM_SCHEMA]`
* Vocabulary schema, when separate: `[VOCABULARY_SCHEMA]`

When a setting is not supplied:

* Use PostgreSQL-compatible ANSI SQL.
* Use only core tables and columns commonly available in OMOP CDM v5.x.
* Use unqualified table names rather than inventing a schema name.
* Clearly identify any dialect-specific function in a SQL comment.

## Read-Only Requirement

The output must consist only of read-only queries.

Do not use:

* `CREATE TABLE`
* `CREATE TEMP TABLE`
* `CREATE VIEW`
* `INSERT`
* `UPDATE`
* `DELETE`
* `MERGE`
* `DROP`
* `ALTER`
* Stored procedures
* User-defined functions

Common table expressions introduced with `WITH` are permitted.

## OMOP Implementation Requirements

Use the appropriate OMOP tables, including only those required by the verified algorithm, such as:

* `person`
* `observation_period`
* `condition_occurrence`
* `procedure_occurrence`
* `drug_exposure`
* `measurement`
* `observation`
* `visit_occurrence`
* `device_exposure`
* `death`
* `concept`
* `concept_relationship`
* `concept_ancestor`

Use valid OMOP column names for the specified CDM version.

### Concept Resolution

Do not invent OMOP `concept_id` values.

When the PDF provides source vocabulary codes:

1. Resolve the source concepts through the `concept` table using the exact `vocabulary_id` and `concept_code`.
2. When necessary, map non-standard source concepts to standard concepts using valid `"Maps to"` relationships in `concept_relationship`.
3. Include the original concept when it is already standard.
4. Include descendants through `concept_ancestor` only when descendant inclusion is explicitly required by the verified algorithm.
5. Do not use concept-name matching when an exact code is available.
6. Do not use `LIKE`, prefix matching, or inferred code ranges unless explicitly required.
7. Preserve the complete code list in the concept-set CTE.
8. Detect vocabulary codes that fail to resolve rather than silently dropping them.

When a vocabulary is not identified in the verified specification, do not guess it. Implement only the portion that can be grounded safely and document the limitation in SQL comments.

### Event and Temporal Logic

Implement exactly:

* Required event counts
* Distinct-date requirements
* Lookback periods
* Follow-up periods
* Washout periods
* Minimum and maximum gaps
* Before-or-after relationships
* Same-day requirements
* Age calculations
* Observation-period requirements
* Encounter or care-setting restrictions
* Provider restrictions
* Laboratory values, units, and abnormality criteria
* Index-date selection
* Exclusion windows
* Case-control precedence

Do not add observation-period, age, visit, or data-quality restrictions unless they appear in the verified algorithm.

Use deterministic logic when multiple qualifying index dates exist. Apply the exact source rule; when the source specifies “first,” use the earliest qualifying date.

### Query Structure

Organize the SQL into clearly labeled sections such as:

1. Configuration and assumptions
2. Source-code concept sets
3. Standard-concept mapping
4. Base eligible population
5. Case criterion events
6. Case aggregation and temporal logic
7. Case exclusions
8. Final cases
9. Control eligibility
10. Control exclusions
11. Final controls
12. Combined phenotype output
13. Vocabulary-resolution quality checks

Use descriptive SQL comments throughout.

Avoid:

* `SELECT *`
* Unqualified ambiguous column names
* Accidental many-to-many joins
* Person duplication
* Unsupported functions
* Implicit date conversions
* Applying filters after a `LEFT JOIN` in a way that unintentionally converts it into an `INNER JOIN`
* `NOT IN` when nullable values could produce incorrect results

Prefer `EXISTS` and `NOT EXISTS` for inclusion and exclusion logic when appropriate.

## Required Result

Return one person-level result set with these columns:

```text
person_id
phenotype_group
index_date
```

Use:

* `phenotype_group = 'CASE'` for cases
* `phenotype_group = 'CONTROL'` for controls

A person must not appear in both groups unless the verified algorithm explicitly permits overlap.

Return at most one row per person per phenotype group unless the phenotype is explicitly episode-based.

When useful for validation, additional evidence columns may be included after the required columns, such as qualifying-event counts or criterion flags. Do not omit the three required columns.

## Missing or Ambiguous Criteria

When an essential detail remains unspecified:

* Do not invent a value.
* Generate the maximal executable query supported by the verified algorithm.
* Mark the limitation in a clearly labeled SQL comment.
* Do not include incomplete predicates or unresolved pseudocode.
* Do not use ellipses.
* Do not ask the user questions.

When the PDF does not define controls, do not create a generic “non-case” control group unless the verified specification explicitly authorizes that definition. Produce the grounded case query and state the control limitation in SQL comments.

## Output Format

Provide:

1. A brief implementation summary.
2. One complete SQL code block containing the read-only executable query.
3. A brief list of grounded implementation limitations, if any.

Do not provide alternative SQL versions unless required for dialect compatibility.
